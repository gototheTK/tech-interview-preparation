1. HikariCP가 무엇인지 설명해 주시겠어요?
	- 수정: HikariCP와 자바나 스프링에서 DB와 TCP 연결을 매번하기에는 무거운 작업이기때문에, 미리 DB와의 커넥션을 만들어 유지하기 위한 소켓 풀인걸로 알고 있습니다. 또한, 멀티 스레드 환경에서 커넥션을 획득할 때 발생하는 스레드 간의 락 경합을 극단적으로 최소화했기 때문에 성능이 압도적이라고 알고 있습니다.
- 
	1. JWT를 활용 하였을 때, AccessToken이 해커에게 넘어갔다고 하면, 이에 대해서 어떻게 대비할 것인가요? 그리고, 로그아웃을 하면은 Token을 어떻게 관리하실건가요?
	- AccessToken이 탈취되었을 때의 피해를 최소화하기 위해 유효기간을 15분 내외로 짧게 가져가고, 재발급 시 Refresh Token도 함께 갱신하는 **RTR(Refresh Token Rotation)** 방식을 도입하겠습니다. 단순히 갱신만 하는 것이 아니라, **서버(Redis)에서 사용된 Refresh Token의 재사용을 감지하도록 설계**하여 해커나 유저 중 누군가 만료된 토큰으로 접근할 경우 **토큰 패밀리를 일괄 폐기(Invalidation)**함으로써 탈취 상태를 감지하고 해커를 강제 차단하도록 대응하겠습니다.
- 
	1. N+1문제에 대해서 설명해주고, 해결방법에 대해서 말해줄래요?
	- N+1문제는 ORM에서 연관된 튜플들을 가져오기 위해서, 부가쿼리가 실행되는 현상입니다. 가령, 부가 상품이 있는 상품을 가져올 때, 상품을 가져오는 쿼리가 실행되고, 부가 상품을 가져오는 쿼리들이 실행됩니다. 그리하여, 트래픽이 몰렸을 때, DB서버에 큰 부하를 주게되는데, 이 현상을 해결하기 위해서, 부가쿼리가 나가지 않도록, 데이터를 한꺼번에 가져오도록하는게 중요한데, OUTER JOIN을 사용하거나, JPA는 JOIN FETCH, MyBatis는 관련 설정을 하는 방법들이 있는 걸로 알고 있습니다.
- 
	1. OUTER JOIN 이나 JOIN FETCH를 사용해 연관된 하위 데이터를 한 번에 가져올 때, 오히려 데이터가 중복되어서 늘어나는 현상(데이터 뻥튀기)이나 페이징 처리를 할 때 주의해야 할 점은 무엇인가요?
	- 일대다관계에서는 FETCH JOIN을 하게된다면, 하이버네이트는 정합성을 위해, 연관데이터를 모두 메모리로가져와서 페이징 처리를 하게되고, 그렇게되면 OOM이 발생하게 됩니다. 이를 예방하기 위해서는, @BatchSize를 걸어주든 default_batch_fetch_size를 적절히 설정하여서, 부가쿼리로 IN을 통해 한꺼번에 가져오도록합니다. 다대일관계나 일대일관계에서는 FETCH JOIN을 사용하여도 됩니다.

	1. Redis를 사용할 때, 주의 사항은 무엇일까요?
	- 제가 아는건 3가지 정도인데, 첫 번째로는 Redis는 싱글스레드이기때문에 처리 비용이 무거운 SMEMBERS나 KEYS같은 명령어 사용에 주의해야합니다. 그리고, 에러가 발생했을 때 데이터가 유실될 때를 대비하여서, 주기적으로 스냅샷을 찍거나 실시간 로그를 남겨서 하드디드스크에 저장하도록합니다. 마지막으로, 프로세스가 에러가 생겨서 운영이 중단되는 떄를 대비하여서, Master와 Replica를 실시간으로 동기화하고, Sentinel을 두어서, Master를 감시하게 하여서, 문제가 생기면 Replica를 승격시키도록하여야합니다.

	1. Redis의 TTL과 Key에 대해서 설명해줄래요?
	- TTL은 Redis의 데이터 저장공간의 존재시간이고, Redis는 기본적으로 Key는 저장공간의 식별자입니다. 제한적인 메모리 공간을 사용하난 Redis에서 무한정 데이터를 쌓아놓지 못하기때문에 Key에 존재시간을 거는것이 중요하다고 알고 있습니다.
- 
	1. Redis의 Set과 List의 차이점에 대해서 설명해줄래요?
	- Set은 중복과 순서를 허용하지 않는 저장소이고, List는 중복과 순서를 허용하는 저장소입니다. 개인 프로젝트에서 Set은 좋아요의 중복을 방어하는데 사용하였고, List는 Write-Back 아키텍처를 설계할 때,d Queue로 사용하였습니다.
- 
	1. 이력서에 JPA를 쓰지 않고, 벌크 연산을 했다고 적혀있던데, 이에 대해서 설명해줄래요?
	- 스프링 스케줄러를 일정시간마다 돌리는 로직을 짜면서, JPA로 save나 saveAll로 처리를 하였을 때, 개별적인 INSERT쿼리가 나가는것을 보았습니다.그래서, 이러한 현상을 알아보니, MySQL 특성상 직접 INSERT를 해봐야 기본키를 얻게된다는 것을 알게되었습니다. 그래서, 이를 한꺼번에 처리하기위해서, Spring에서 제공하는 JDBC를 사용하였고, 영속성 컨텍스트에 무거운 스냅샷을 만들필요도, 단건의 ISNERT를 개별적으로 계속 날리는 문제도 없이 한꺼번에 적재하거나 삭제하도록 하였습니다.
- 
	1. 멀티 스레드 부하 테스트 및 트랜잭션 격리 문제 해결에 대해서 자세히 설명해 주실래요?
	- 제가 예전에, 테스트코드로 동시성을 검증하려고 할 때, @Transactional 어노테이션을 걸어서 파생스레드를 만들어 동시에 많은 이력을 하는 로직을 검증하려고 했습니다. 그렇다보니, 자식 스레드들이 메인 스레드의 커넥션을 공유받지 못하고 각자의 커넥션으로 데이터를 커밋해려서, 메인 스레드가 롤백되어서, DB에 커밋된 데이터가 그래도 남아버리는 사태가 발행새 테스트 코드의 멱등성이 깨져버리는 사태가 발생했었습니다. 이를 해결하기 위해서, JDBC를 이용하여서, 수동으로 적재한 데이터를 삭제하였습니다.
- 
	1. JPA의 단점을 극복하기 위해 Spring JDBC로 벌크 연산을 구현하셨습니다. 그렇다면 벌크연산으로 수만 건을 밀어 넣었을 때, 적절한 Batch Size는 어떻게 결정하셨나요?
	- 어떤 상황을 상정하고 적절한 Batch Size를 설정은 하지 않았었습니다. 다만, Batch Size가 커져버리면 메모리에 부하를 많이 준다는걸 인지하고 있었기 때문에 1000개 정도로 설정하였습니다.
- 
	1. 테스트코드 작성 시 @Transactional 롤백 문제를 겪고 수동 TRUNCATE로 해결하셨습니다. 혹시 Tescontainer나 인메모리 DB(H2)를 활용해 테스트 환경 자체를 격리하는 방법은 고려해 보지 않으셨나요?
	- 맨 처음에 H2를 활용해 코드를 짰지만, 실제 DB에서는 어떻게 결과가 나오는지 알기 위해서 MySql를 설치해 직접 데이터를 적재하였습니다. 다만, TestContainer에 대해서는, 그 당시에는 도커에 대해서 제대로 이해를 못했기 때문에 고려하지 못했습니다.
- 
	1. 동시성 제어를 락(Lock)을 고민하셨을 텐데, 비관적 락(Pessimistic Lock)과 낙관적 락(Optimistic Lock)의 차이는 무엇이며 실무에서는 어떤 기준으로 선택해야 할까요?
	- 비관적 락은 어플리케이션에서 DB에 직접 락을 거는 락이고, 낙관적 락은 추적 컬럼을 테이블에 설정하여서, 추적 컬럼의 변화 유무에 따라 예외를 발생시켜서 몇 번 더 시도하는 락입니다. 비관적 락은 결제나 주문과 같이 정합성이 중요한 로직에 적합하고, 낙관적 락은 게시판의 좋아요와 같이 정합성보다는 속도가 중요한 곳에 적합하다고 생각합니다.
- 
	1. MySQL 엔진의 기본 격리 수준이 무엇인지 아시나요? 정산 시스템에서 Repeatable Read를 사용할 때 발생할 수 있는 현상이나 주의점이 있을까요?
	- Repeatable Read는 직접 DB로부터 데이터를 읽어오는 격리성 수준입니다. 그래서, 트랜잭션중에서 다른 트랜잭션에서 데이터를 INSERT를 한다면, 없던 데이터가 생겨가는 팬텀 리드현상이 발생할 수 있습니다. 그러나, MySQL은 Undo Log로 부터 트랜잭션 시작 이전의 데이터를 읽어오므로, 팬텀리드의 현상을 원천적으로 차단합니다. FOR UPDATE와 같은 베타적 락을 걸고 조회할 경우에 성능적인 문제가 생기는데, 왜냐하면 이러한 락을 걸 경우에 하나의 튜플 뿐만 아니라 앞 뒤의 공간에도 락을 걸어서 팬텀리드를 방지하려고 하기때문입니다.
- 
	1. N+1 문제를 겪으셨는데, JPA의 FetchType.LAZY의 내부 동작 원리를 프록시(Proxy)객체와 연관 지어 설명해 주실 수 있나요?
	- JPA는 LAZY 방식으로 연관 데이터를 가져오면, 바로 가져오지 않고, 텅빈 프록시 객체를 주입해 놓습니다. 그러다가, 로직에서 실제 사용되면은 DB에 쿼리를 날려서 데이터를 채우는 걸로 알고 있습니다.
- 
	1. 인덱스를 타지 않는 쿼리(Table Full Scan)의 대표적인 케이스는 어떤 것들이 있을까요?
	- 제가 아는건, 복합 컬럼으로 인덱스를 만들었을 경우, 맨 좌측의 컬럼이 조건절에 없었을 때입니다. 그럴 경우에, 인덱스를 타지 않고, 처음부터 테이블을 스캔하는걸로 알고 있습니다.
- 
	1. Indie Platform 프로젝트에서 단일 DB 병목을 막기 위해 Redis Write-Back 아키텍처를 직접 설계하셨네요. 아주 흥미롭습니다. 스케줄러가 Redis의 데이터를 DB로 밀어 넣는(Write-Back) 그 찰나의 순간에 서버가 죽거나 새로운 요청이 들어올 때, 데이터 유실(Lost Update)이나 중복 적재를 막기 위해 구체적으로 어떤 자료구조와 명령어(전략)를 사용하셨는지 설명해 주시겠어요?
	- 데이터 유실과 중복을 막기 위해서, 두 가지 전략을 사용했습니다. 첫째는 적재하는 공간과 DB에 반영하는 공간을 분리하기 위해서, 스케줄러로 반영시에는 저장소의 Key를 바꾸는 전략을 사용하였습니다. 그리고, 실제 적재를 할 때는 POP하는 대신에 복사를 하여서 반영 한 후에 해당 데이터를 삭제하도록 하였습니다. 마지막으로, 중복을 막기위해서는 INSERT IGNORE를 사용하였습니다.
- 
	1. 멀티 스레드 부하 테스트를 진행하면서 `@Transactional`을 제거하고 수동 롤백을 구현하셨다고 적혀있습니다. **스프링 환경에서** **`@Transactional`****을 건 상태로 파생 스레드를 생성했을 때 왜 격리성이 깨지는 문제가 발생했는지 프레임워크의 내부 동작 원리(ThreadLocal)와 연관 지어 설명해 주시고, 수동으로 멱등성을 보장한 과정도 말씀해 주세요.**
	- 스프링의 @Transactional은 현재 스레드의 ThreadLocal에 DB Connection을 저장하여서, 사용하는걸로 알고있습니다. 그래서, 동시성 검증을 위한 테스트코드를 작성할 때, 메인스레드와 파생스레드에 모두 @Transactional 어노테이션을 거다보니까, 제 각각 DB Connection을 사용하게 되고, 커밋 시점이 달라져, 테스트의 격리성이 깨져버리는 문제가 발생하였습니다. 메인스레드에 @Transactional을 제거하고, Spring에서 제공하는 JDBC를 이용해 수동으로 TRUNCATE 쿼리를 날렸습니다.
- 
	1. JPA 프록시 원리를 잘 이해하고 계시네요. 그럼 한 클래스 내부에서 @Transactional이 없는 메서드가 동일 클래스 내부의 @Transactional이 붙은 메서드를 호출하면 롤백이나 트랜잭션이 작동하나요?
	- 스프링의 AOP는 프록시 디자인패턴을 따릅니다. @Transactional을 선언하면, 서비스 객체를 DB 처리를 하는 객체로 감싸서, 불러오도록하는데, 외부가 아니라 내부에서 자가 호출을 해버리면, 프록시 객체를 타지 못하게 됩니다. 이를 해결하기 위해서는 별도의 서비스 클래스로 구조를 변경해야 합니다.
- 
	1. 이전 트러블슈팅 경험에서 TestContainer를 고려하지 못했다고 하셨는데, 현재, Docker에 대해 학습하셨다면, 애플리케이션 Docker로 컨테이너화했을 때 얻을 수 있는 실무적인 장점은 무엇이라고 생각하시나요?
	- 도커는 운영체제의 커널단은 그대로 사용하되, 어플리케이션단을 격리하여서 환경변수나 포트번호등을 수정할 필요가 없게 만들어주는 걸로 알고있습니다.
- 
	1. 자바에서 코틀린으로 넘어가고 계신데, 두 언어를 모두 써보면서 느낀 코틀린만의 백엔드적인 장점은 무엇이라고 생각하시나요?
	- 코틀린을 써보면서 느낀건, Null Point Exception검사 조건이 까다러워서, 완전히 컴파일에 성공하면은 운영했을 때, Null point Exception때문에 고생할 일은 없겠구나라고 느껴졌습니다.

	1. MyBatis와 JPA의 차이점에 대해서 설명해주세요.
	- MyBatis는 데이터 중심의 쿼리 매퍼이고, JPA는 도메인 중심의 ORM 입니다. MyBatis는 정밀한 SQL문이나 프로시저와 같은 DB 중심의 처리에 적절하고, JPA는 결제나 주문처럼 도메인의 상태 관리같이 객체지향적인 로직에 적절합니다.
- 
	1. 베타적 락과 공유적 락과 비관적 락과 낙관적 락의 차이점은 무엇인가요?
	- 베타적 락과 공유적 락은 DB쿼리로 튜플에 직접 락을 거는 방법으로서, 다른 트랜잭션이 쓰거나 읽는걸 방지합니다. 그에 비해, 비관적 락과 낙관적 락의 차이점은 DB 락의 사용 유무 입니다. 비관적 락은 DB 락을 직접 사용하는것이고, 낙관적락은 추적 컬럼을 설정하여서 트랜잭션중에서 추적컬럼의 변화를 보고, 예외를 발생시킵니다.
- 
	1. JPA cascade = CascadeType.REMOVE 와 orphanRemoval = true의 차이점은 무엇인가요?
	- orphanRemoval = true는 엔티티에서 자식 엔티티를 삭제가 반영되지만, CascadeType.REMOVE는 부모 엔티티가 삭제 삭제될 때, 반영됩니다. 그렇기 때문에, orphanRemoval = true를 사용할 때는 주의하여야합니다. 그렇지 않다면, 여러 데이터가 참조하는 자식데이터가 유실될 수 있기 때문입니다.
- 
	1. 비동기 처리와 동기 처리에 대해서 설명해주시겠어요?
	- 처리가 처리의 응답을 기다리는 것이 동기 처리이고, 처리가 처리의 응답을 기다리지 않고, 콜백이든 메세지큐등을 통해서 응답을 받는 방식입니다. 실시간, DB의 정합성이 필요한곳은 동기 처리가 적절하고, 당장의 DB의 정합성보다는 속도와 성능이 더 중요한곳은 비동기처리가 적절하다고 생각합니다.

### 심화

- 
	1. Sentinel군집에 문제가 생겼을 때 어떻게 대처하시겠어요?
	- 솔직히 말씀드리자면, 실무에서 대규모 트래픽을 운영하면서 Sentinel 군집이 모두 붕괴되는 장애를 겪어본적이 없기때문에 여기에 대해서는 정확히 말씀드릴 수 없을거 같습니다. Sentinel이 이상이 생겨도 Redis는 돌아가는 걸로 알고있지만, 그래도 이러한 모니터링 프로세스가 중요하다면, Sentinel에 이상이 생겼을 때 어다인 때의 경험을 살려, 쉘 스크립트로 Sentinel을 감시하고, 알림을 만들어볼거 같습니다.
- 
	1. 만약 서버 운영 중에 이상이 생겼을 때 어떻게 대응하시겠어요?
	- 서버 장애 대응에 대해서는 제가 경험해본 바가 별로없어서 정확히는 말씀드리지 못할거같습니다. 다만, 최대한 경험을 통해 말씀드리자면, 먼저 롤백부터하고, 스카우터와 같은 모니터링 프로그램으로 로그로 해당 서비스를 추적하여 분석하여서, 트랜잭션 에러라면은 코드를 적절히 수정하여서 해결할거 같고, ConnectionTimeoutException과 같은 지연현상이라면, 스레드풀 고갈인지, API지연현상인지 분석해 볼거 같습니다.
- 
	1. 전 회사에서 Scouter를 사용해 에러를 잡으셨다고 했는데, 당시 주로 확인했던 지표는 무엇인가요? 병목지 지점은 구체적으로 어떻게 추적해 내셨나요?
	- 너무 오래 되었고, 그다지 많이 사용하지 않아서 여기에 대해서 정확히 답해드릴 수는 없겠습니다. 다만, 모니터링화면에서 오류가 생기면 빨간 동그라미가 발생하는데, 그 빨간 동그라미를 클릭하여서 관련 로그를 확인하고, 로직을 수정한 경험은 있습니다.
- 
	1. 대용량 트래픽 상황에서 DB 병목이 의심될 때 Slow Query Log를 보겠다고 하셨습니다. 그렇다면, 그 Slow Query를 발견한 후에는 어떻게 튜닝(최적화)하시겠습니까?
	- 제가 Slow Query Log를 직접 사용해보지 않아서, 잘모르겠습니다. 다만, 최근에 배운 지식을 바탕으로 추론해서 말씀을 드리자면, 쿼리에 문제가 생겼다 싶으면, EXPALIN을 질의어를 통해서, FULL TABLE Scan이 나는지 혹은 인덱스에 문제가 있는지 확인해보겠습니다.
- 
	1. OOM(Out Of Memory)을 겪어보고 해결하셨는데, OOM이 발생했을 때 서버가 뻗는 것을 방지하기 위해 JVM 메모리(Heap) 설정이나 GC(Garbage Collector) 튜닝을 고민해 본적이 있나요?
	- JVM 튜닝에 대해서는 경험이 없어서 잘모르겠으나, OOM을 겪어보고 해결한 경험은 앞에서 말씀 드렸다 시피, 다량의 데이터를 MySQL에 적재하고자 savaAll을 실행하였을 때, OOM이 발생하였고, JDBC로 해결한 경험입니다.
- 
	1. 웹 에이전시나 개인 프로젝트에서 외부 API를 연동해 본 경험이 있나요? 만약 연동 중인 외부 서버가 장애가 나서 응답이 지연된다면, 우리서비스까지 장애가 전파되는 것을 어떻게 막으시겠습니까?
	- 전 회사에서 PG사와 연동하여서, 결제를 처리한 적이 있는데, 이 때는 시간제한을 두어서 해결하였던거 같습니다. 이에 대한 로직은 제가 직접 짠것이 아닌 기존 로직이기 때문에, 정확히 말씀드릴 수가 없을거 같습니다. 그러나, 최근 배웠던것을 최대한 이용한다면, 파생스레드나 다른 스레드풀에게 외부 API 처리를 넘겨서 시간제한을 두어, 비동기처리를 하도록하겠습니다. 덧붙이자면, 결제 같은 경우 타임아웃이 발생하여서 실패를 한다면, 상태를 확인하여서 결제 취소를 시도해서 정합성을 지키도록 하겠습니다.
- 
	1. 데이터베이스에서 샤딩이란 무엇인가요?
	- 제가 경험해보지 않아서, 정확하게 말씀드릴 수 는 없지만, 제가 아는 것들을 바탕으로 말씀드리자면, 거대한 DB 테이블을 여러 DB서버로 분리해서, 저장하고 관리하는 기술인걸로 이해하고 있습니다. 왜 이렇게 하는거냐면, DB는 무겁고, CPU를 많이 잡아먹는 프로세스이기 때문입니다. 또한, 성능을 위해서 중복을 허용하는 역정규화도 고려할 수 있습니다.
- 
	1. 도메인이 나뉘어져 있는, 환경에서 프로세스와 프로세스같은 교류와 요청에 대해 적절한 프로세스에게 전해줄려면 어떻게 해야할까요?
	- 이 질문은 MSA에 대한 이해를 확인하시려는 의도로 질문하신거 같습니다. 제가 MSA에 대한 경험이 없어서 이에 대해 정확하게 말씀드리지는 못합니다. 다만, 제가 학습한 지식을 바탕으로 말씀드리자면, 외부요청에 대해서는 API 게이트웨이를 두어서, HTTP의 URI나 헤더를 분석하여 적절한 프로세스를 찾아서 전달하도록 하겠습니다. 그리고, 프로세스간의 교류에 대해서는 결제 후 의 정산, 수정같은 처리는 메세지큐를 활용하여, 이벤트 처리 방식으로 비동기처리를 하도록하고, 조회와 같은 즉각적인 처리에 대해서는 REST API를 호출하여 동기적으로 처리하도록 하겠습니다.
- 
	1. 스프링과 스프링부트의 차이점은 무엇인가요?
	- 다중 컨텍스트를 지향하느냐 단일 컨텍스트를 지향하느냐에 따른 설정의 간략화가 차이점인걸로 알고있습니다. 기존의 스프링에서는 비즈니스 처리를 하는 application-context와 웹 요청 처리를 하는 servlet-context로 나뉘어져 있었고, 여러 컨텍스트를 만드는걸 지향하였습니다. 그러다보니, 톰캣에 여러 서블릿을 등록하고, 컨텍스트에 매핑해주등 설정이 복잡하였습니다. 반면에, 스프링부트는 비즈니스 처리든, 공통 처리든 통합하여서, 설정을 간략화하였습니다. 또한, 톰캣을 내장하여서 war 설정 필요 없이, jar파일 하나만으로 실행할 수 있도록 환경을 최적화하였습니다.
- 
	1. 이력서에 무중단 CI/CD를 적어주셨는데, 어떻게 구현하셨나요? -
	- 죄송합니다. 실제로는 무중단으로 CI/CD를 구축하지는 않았습니다. 그렇지만, 왜 그렇게 썼고 질문을 하신다면, 제가 이력서의 초안을 작성하고, GitHub을 연동하여서, AI에게 이력서를 첨삭해달라고 부탁하였습니다. 그러다보니 무중단이라는 단어가 붙게 되었는데, 그 당시 저는 Redis를 활용한 비동기처리에 집중했기 때문에, 용어의 무게감을 인지하지 못하고 대수롭지 않게 넘겼습니다. 그러나, 며칠 전 면접에서 이에 대한 지적을 받게 되었고, 즉각적으로 이력서를 수정하였습니다. 그리고, 무중단 CI/CD가 무엇인지 알았습니다. 구체적으로 말씀 드리자면, EC2에 포트만 다르게하여 2개의 프로세를 띄우고, 빌드하여 반영할 때 마다, Nginx가 바라보는 프로세스만 바꾸어서 운영하는것입니다.
